# AMPLIFY-OS — общие инструкции для ИИ-агентов

Своя ОС с нуля (не Linux): ядро x86_64 на C и NASM, без libc и libgcc,
загрузка через GRUB2 Multiboot2 или свой UEFI-загрузчик. Здесь — правила
работы. Факты о проекте сюда не переписаны, чтобы не устаревать в двух местах:

- `CLAUDE.md` (корень) — окружение, архитектура, грабли, статус этапов,
  тесты, ограничения. Прочитать целиком до первой правки.
- `.claude/skills/amplify-os/SKILL.md` — пошаговые процедуры: сборка, QEMU,
  headless-тест, новый модуль / команда shell / экран, узел Proxmox, отладка
  зависаний. Это обычный Markdown — читать как документ, даже если агент не
  умеет «скиллы».
- `docs/archive/CLAUDE_full_2026-09-26.md` (230 КБ) — история этапов и
  хотфиксов. Только при разборе старых решений и только нужный раздел
  (сначала список заголовков `^## `).

Если что-то расходится: прав код, затем `CLAUDE.md`, затем этот файл.

# Общие правила

- Отвечать пользователю по-русски.
- Комментарии в коде — по-русски, подробно, объясняют ПОЧЕМУ, а не только
  ЧТО. У нового файла — шапка: что это, зачем, как связано с соседними слоями
  (образец — `kernel/arch/x86_64/netcfg.c`).
- Существующие комментарии не удалять, если они не относятся прямо к тому,
  что меняешь.
- Заметил ошибку, не связанную с задачей, — попутно не чинить: назвать в
  отчёте (файл, функция, симптом, как увидеть) и предложить отдельной задачей.
  Известные чужие warnings без задачи не трогать: `gles.c` и `app_glcube.c`
  (misleading-indentation), `amply.c` (`s_strcat` unused).
- Строго поэтапно: без подтверждения пользователя следующий этап не начинать.
- Не хардкодить факты — сверять с кодом. «Работает» — только после прогона
  теста; провалы называть прямо, ограничения (`CLAUDE.md` §8) не замалчивать.
- Стиль ОС не упрощать: бренд AMPLIFY-OS, треугольный логотип, «мистические»
  имена команд и папок (`scan`, `engrave`, `weave`, `/disk/Sanctum`…).
- Беречь токены: короткие команды, вывод через фильтр, без циклов опроса и
  длинных ожиданий.

## Где искать

Дерево небольшое, но в нём два ядра с одинаковыми именами файлов и 7 ГБ
артефактов — поиск без указания каталога находит не то.

- Действующий код: `kernel/kernel64_main.c` (точка входа, smoke-блоки),
  `kernel/arch/x86_64/` (всё ядро — плоский каталог, 280 файлов), `uefi/`
  (наш BOOTX64.EFI), `libc-x86_64/`, `userspace/x86_64/`, `tools/`
  (хост-утилиты, генераторы, эталоны MIND), `scripts/` (тесты и узел
  Proxmox), `amply_pkgs/`, `boot/grub-x86_64.cfg`, `Makefile.x86_64`,
  `linker_x86_64.ld`.
- Наследие (i386, этапы 1–36, «MyOS») в сборку x86_64 не входит и ею не
  подключается: `kernel/arch/i386/`, остальные подкаталоги `kernel/`
  (`drivers`, `fs`, `gui`, `net`, `shell`…), `kernel64/`, `libc/`,
  `userspace/` кроме `x86_64/`, а из корня — `README.md`, `STAGE*`,
  `docs_STAGE*`, `SUMMARY.txt`, `setup.sh`, `quickstart.sh`. Там лежат 48
  одноимённых `.c` (`kernel/net/tcp.c`, `kernel/gui/wm.c`,
  `kernel/shell/shell.c`…) — править их по ошибке легко, а толку не будет.
- В `build/` не искать: образы дисков, ISO, модели, логи прогонов.
- Перед работой в каталоге прочитать его описание:
  `libc-x86_64/` — `libc-x86_64/README.md`; сеть через TAP/мост —
  `docs/network_tap.md`; экраны Pearl — `ui_reference/` (17 референсов и
  `reference_manifest.json`) и `REDESIGN_HANDOFF_RU.md`; установщик — макет
  `amplify-os-installer.png`.
- Объявление функции ядра — в `kernel/arch/x86_64/<модуль>.h`; попал ли
  символ в ядро — `nm build/kernel-x86_64.bin | grep <имя>`.
- Не нашёл быстро — спросить пользователя, а не перебирать диск.

## Инструменты

- Всё собирается и запускается в WSL (Debian). Из Git Bash или PowerShell:
  ```
  wsl -e bash -lc "cd /mnt/d/OS2 && <команда>"
  ```
  Команду начинать с `cd …`: Git Bash переписывает аргументы, начинающиеся
  с `/`, в пути Windows.
- `make -f Makefile.x86_64 <цель>` (то же, что `make ARCH=x86_64 <цель>`) —
  главный интерфейс сборки:
  - `all` — ядро, initrd, установочный ISO, `esp.img`, dev-диск;
  - `build/kernel-x86_64.bin` — только ядро (проверить, что собирается);
  - `iso` — установочный ISO (BIOS + UEFI + USB); `dev-iso` — маленький
    UEFI-образ с новым ядром для ВМ 402;
  - `bootefi`, `esp` — UEFI-загрузчик и ESP-образ; `sysroot`, `libc-test` —
    libc; `mind-model` — модели MIND на dev-диск;
  - `run`, `run-installer`, `run-installed`, `installer-disk-reset` — запуск
    в QEMU; `clean`.
- Форматтера и линтера нет (ни `.clang-format`, ни `.editorconfig`): стиль —
  как в соседнем коде, предупреждения компилятора читать самому.
- Проверки после сборки: `nm build/kernel-x86_64.bin | grep ' U '` — пусто
  (libgcc нет); толщина кадров стека — сборка с
  `CFLAGS_EXTRA=-fstack-usage`, файлы `.su`.
- Тесты — `scripts/test_stageNN_<имя>.sh`: QEMU без окна, serial в файл,
  клавиши и скриншоты через монитор/QMP. Что каждый проверяет и сколько в нём
  проверок — `CLAUDE.md` §7.
- Узел Proxmox (сборка и все тяжёлые прогоны, KVM) — из Git Bash:
  - `bash scripts/pve_test.sh <имя> <тест> [clean]` — отправить исходники,
    собрать, запустить тест в фоне; `<тест>` = `pve_regression` — вся
    регрессия, `pve_net_suite` — сеть и обзор настоящих сайтов;
  - `bash scripts/pve_wait.sh <имя>` — ждать конца на узле (запускать в
    фоне); `bash scripts/pve_test.sh --log <имя>` — показать лог;
  - `bash scripts/pve402_deploy.sh <имя>` — новое ядро на ВМ 402;
  - `bash scripts/pve_run.sh <файл.sh>` — выполнить свой скрипт на узле.
  Имя запуска каждый раз новое. При обрыве шлюза скрипт повторяется с
  начала: удалённые команды короткие и идемпотентные, опасные шаги закрыты
  файлом-маркером. Адреса, права `ai`, конфиг ВМ — `CLAUDE.md` §2.
- Если у агента подключён MCP-сервер `proxmox` — им удобно смотреть статус и
  конфиг ВМ, хранилища, журнал задач; менять что-либо — только через `qm` по
  ssh, как описано в `CLAUDE.md` §2.
- Python: в WSL его нет, есть у Windows (`python`; PIL, numpy, torch). Из WSL
  он не запускается — эталоны и конвертацию PPM → PNG считать из Git Bash.
- Интернет — только у Windows; в WSL его нет.
- Код с `\n`, `\x..`, `\\` и патч-скрипты писать файлом, а не heredoc'ом в
  Bash: heredoc съедает обратные слэши и в C, и в python.

## Истории в git нет

Репозиторий не под git: нет ни `git log`, ни `git diff`, ни отката.

- Что и зачем менялось — `CLAUDE.md` §6 (этапы), §7 (прогоны), §5 (грабли),
  дальше архив; в коде — пометки этапа в комментариях (`[41.2]`,
  `[этап 44]`).
- Перед крупным удалением или массовой правкой — сделать копию затронутых
  файлов и сказать пользователю, где она лежит.
- Массовая правка — python-скрипт с `assert count == 1` на каждую замену. Он
  не идемпотентен: упал на середине — остаток применять отдельным скриптом,
  а не перезапуском.
- `scripts/pve_sync.sh` не стирает на узле файлы, которых больше нет в
  исходниках: после удаления или переименования исходника почистить каталог
  на узле, иначе там соберётся старое.

## Ссылки на код в отчётах, CLAUDE.md, комментариях и тестах

- Ссылаться на имя, а не на место: функция, `#define`, цель make, ключ
  конфига, команда shell, маркер serial. Файл — без номера строки, без
  «правила выше X». Такой текст живёт дольше кода: архивная памятка называла
  список исходников «`Makefile.x86_64:56-123`» (сейчас он кончается на 215-й
  строке), а комментарий в `Makefile.x86_64` до сих пор отсылает к «CLAUDE.md
  §14.13» — раздела с таким номером больше нет.
- Номер раздела `CLAUDE.md` — тоже позиция: в коде и тестах называть граблю
  по сути («prerequisite-списки раскрываются при чтении правила»), номер —
  только в самой памятке и в отчёте.
- Где место действительно помогает: в отчёте пользователю `файл:строка`
  уместно (его читают сейчас), в постоянном тексте — имя файла и цитата
  нужных строк.
- Строки serial — интерфейс тестов: `[smoke NN] … PASS/FAIL`,
  `[mesh] layout`, `[browser] page`, `[anim] … fps=N`. Поменял текст строки —
  найти её в `scripts/` и поправить тесты тем же изменением.
- Этап называть номером: «этап 49», «подэтап 48.2»; его тест —
  `scripts/test_stage49_<имя>.sh`, его smoke-блок — `[smoke 49]`.

## Стиль кода

- Отступ 4 пробела, UTF-8, LF. Include guard — `AOS_X86_64_<ИМЯ>_H`. Имена —
  `модуль_действие` (`netcfg_boot`, `fat32_bind`), состояние файла —
  `static g_*`.
- libc и libgcc нет: свои `s_len` / `s_copy`, печать через `serial_puts` /
  `serial_print_dec`; builtins вроде `__builtin_popcount` — своей функцией.
- В строковых литералах C — только символы CP1251 (GCC перекодирует
  литералы): эмодзи, `→`, `×`, псевдографика ломают сборку. В комментариях
  стрелки допустимы. Эмодзи не использовать нигде.
- Стек ядра 32 КБ: буфер больше ~4 КБ — `static` или `kmalloc`.
- Секреты — через `crypto.h`: `crypto_wipe`, `crypto_eq_const`,
  `crypto_rand_bytes`.
- Код на AP (`smp_pool_parallel_for`) — только вычисления над заранее
  выделенной памятью. Сеть разбирается в прерывании: общее с обработчиком —
  под `net_irq_save`, ждать в обработчике нельзя.
- Имена команд shell и папок ОС — в «мистическом» стиле; новая команда — и
  в диспетчер `shell_exec_line`, и в `cmd_guide()`.
- Остальное, что уже стоило часов, — `CLAUDE.md` §5; перечитать перед правкой
  загрузки, памяти, дисков, сети, MIND.

## Порядок работы

- Копия исходников на узле (`/tmp/ai-work/OS2`) — tmpfs: устаревает после
  каждой правки на ПК и пропадает при перезагрузке узла. `pve_test.sh`
  синхронизирует сам; при ручной сборке сначала
  `PVE_WORK=/tmp/ai-work bash scripts/pve_sync.sh`. ISO, собранный на другой
  машине, — другой ISO: после переноса сборки гонять тест установщика.
- На ПК пользователя — сборка и короткий smoke (1–2 минуты). Тесты, замеры и
  всё, что под TCG идёт часами, — на узле под KVM. Вся регрессия
  (`pve_regression`) — перед отчётом о завершении этапа.
- Вывод долгих команд (тест, регрессия, обзор сайтов, замер) не пропускать
  через `tail` / `grep` / `head` на лету: он должен лечь в файл, из которого
  потом читается нужное, — иначе ради другого фрагмента придётся гонять всё
  заново. Локально — файл в `build/` (`/tmp` в WSL — tmpfs и очищается);
  тесты сами складывают serial и скриншоты в `build/screens-<этап>/`, на
  узле — `build/reg/<тест>.log` и итог `build/reg/summary.txt`. Быструю
  сборку фильтровать можно, с кодом возврата: `…| grep -iE ' error|warning';
  echo BUILD=${PIPESTATUS[0]}`.
- Конец прогона на узле не опрашивать с ПК — `pve_wait.sh` в фоне.
- Пересобирать ровно то, что затронуто:
  - только `scripts/`, `tools/*.py`, документы — ничего;
  - `.c` ядра — `build/kernel-x86_64.bin`, для запуска `all` (или `dev-iso`
    для ВМ 402);
  - `struct` / `#define` в заголовке — сначала `rm -rf build/x86_64/kernel`
    (на узле — параметр `clean`): зависимости от заголовков не отслеживаются;
  - флаги в `Makefile.x86_64` — `rm -rf build/x86_64`;
  - `uefi/main.c` — `bootefi` и `esp`, затем тест установщика;
  - `libc-x86_64/`, `userspace/x86_64/` — `sysroot`, `libc-test`;
  - арифметика `mind_*.c` — повторить в `tools/mind_ref.py` и пересчитать
    эталоны.
  Генерируемое руками не править: `crypto_ca_blob.c` —
  `scripts/gen_ca_blob.sh`, `mind_unicode.h` — `tools/gen_unicode_tables.py`.
- Тесты — только без окна (`-display none`). `make … run` открывает окно GTK
  и ждёт человека: это команда для пользователя. Новому тесту — свой порт
  монитора (4577–4595 заняты: регрессия гоняет тесты параллельно).
- Зелёный итог ещё не значит «всё проверено»: сверять ЧИСЛО проверок с
  `CLAUDE.md` §7. Тест 48 без исполняемого `build/luks_interop` молча
  пропускает сверку с libcryptsetup (23/23 вместо 25/25, после переноса с ПК
  нужен `chmod +x`); без интернета на узле проверки DNS/TLS уходят в SKIP;
  тест 45 в WSL даёт 24/25 — там нет python3.
- Без явного «да» пользователя никогда:
  - начинать следующий этап;
  - менять что-либо на ВМ 403 (Test-RTR);
  - трогать диск пользователя `vm-402-disk-4.qcow2` и выполнять
    `qm set 402 --delete unusedN` — это уничтожает том;
  - делать крупные удаления в дереве.
- Обход блокировок сайтов не делается вообще; «сайт не открылся» разбирать
  по `SKILL.md`, раздел про браузер, TLS и сеть.
- Завершение этапа: новый тест проходит целиком → регрессия → обновить
  `CLAUDE.md` §6 и §7 (и §5, если нашлась новая грабля) → отчёт по-русски с
  цифрами тестов и ограничениями → вопрос «Этап N завершён. Всё работает?
  Переходим к N+1?».
